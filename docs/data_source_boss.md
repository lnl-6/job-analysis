# 数据源：Boss 直聘岗位数据（口径、采集与边界）

> 一句话：**数据源从「问卷」换成了「岗位」，但分析内核一行没改**——
> 统计推断、样本量门槛、数据质量体检、口径治理、阻断式门禁、不做预测，全部原样保留。
> 换的只是「同一批列名背后到底在测什么」，而这件事必须写在数字旁边，所以有这份文档。

---

## 1. 为什么要换（三个参考项目的核心与它们的短板）

工作区里的三个参考项目（`bosszp`、`bosszp-selenium`、`Boss_zhipin_spider`）把同一件事做了三遍：

| 项目 | 采集姿势 | 存储 | 呈现 | 字段 |
| --- | --- | --- | --- | --- |
| `bosszp` | Scrapy + 手工粘贴 Cookie（`__zp_stoken__`）+ 下载延迟 60s | CSV → pandas 清洗 → MySQL 单表 `t_boss_zp_info` | Flask + Highcharts 大屏 |
| `bosszp-selenium` | Selenium 打开浏览器、点分类、滚动页面 | MySQL 宽表 `job_info`（15 列，含技能、抓取时间） | 截图 |
| `Boss_zhipin_spider` | Scrapy + requests，302 时**手输验证码** | MongoDB / JSON | Jupyter + ECharts、词云 |

**它们的核心（值得继承）**

1. 岗位字段的抓取口径基本一致：岗位名、薪资字符串（`15-25K·13薪`）、城市（`北京·海淀区·中关村`）、学历要求、经验要求、公司行业/融资/规模、福利标签、技能标签；
2. 流程一致：采集 → 清洗 → 入库 → 分析/呈现；
3. 清洗规则值得借鉴：地址拆三级、薪资拆上下界、经验/规模编码、福利标签分词。

**它们的短板（正是本项目已有的东西）**

- 没有测试、没有 CI；Cookie 和数据库密码硬编码在源码里；
- 只有一张宽表，没有分层；没有字段校验、没有幂等、没有质量门禁；
- 分析只有计数与占比（`GROUP BY + COUNT`），**没有统计推断**：不说置信区间、不说 p 值、不说效应量；
- 没有溯源：报告里的数字既没有数据指纹，也不知道是哪次运行、用了什么阈值；
- 反爬策略脆弱：Cookie 过期即失效、断点续爬要重写代码、302 靠人手输验证码；
- 薪资解析不严谨：`K` 与 `万` 混用、`·13薪` 被丢掉、`元/天` 直接当元处理。

所以本项目的做法不是重写一个爬虫，而是**把它们的采集能力接进一条「可验证」的流水线**：

```
scripts/crawl_boss.py          抓取（低频、可断点续爬、原始响应落 JSONL）
        ↓  data/raw/boss/raw_jobs.jsonl          （ODS 层：只落地，不改数据）
src/sources/boss.py            口径适配（原始 → 7 列分析契约 + 岗位侧扩展列）
        ↓  data/raw/boss_岗位数据集.csv          （analysis-ready）
src/loader.py → cleaner.py → analysis.py → report.py
        ↓
output/report.md + 9 张图 + SQL 层（ODS/DWD/ADS）+ Power BI
```

**关键设计：抓取与解析分离。** 原始 JSON 完整落盘，口径改了重跑适配层即可，不必重爬；
这也意味着「口径错误」是可回溯、可修复的，而不是埋在爬虫里。

## 2. 字段映射（这份表是整个数据源切换的契约）

| 分析契约列 | 问卷口径（原数据源） | 岗位口径（本数据源） | 规则 |
| --- | --- | --- | --- |
| `学历` | 受访者学历 | **岗位要求的学历** | 大专/本科/硕士/博士 → 同名；中专/高中/初中/学历不限 → `不限` |
| `专业` | 所学专业 | **岗位方向** | 按标题关键词映射：数据分析 / 数据开发 / 算法 / 数据治理 / 数据产品 / 其他（规则见第 4 节） |
| `期望薪资` | 受访者期望月薪 | **岗位薪资区间中值（元/月）** | 解析规则见第 3 节；`面议` 留空，由清洗层按中位数填充并标记 `salary_is_filled` |
| `满意度评分` | 受访者满意度 | **岗位吸引力代理分（0~5，proxy）** | 公式见第 5 节。**不是满意度**，不可与问卷口径混用 |
| `是否有实习经历` | 在校是否实习过 | **岗位是否面向实习/应届** | 岗位类型 ≠ 社招 → `是`，否则 `否` |
| `毕业去向` | 就业/考研/出国/创业/待业 | **岗位类型** | 实习 / 校招 / 社招 |
| `工作城市` | 期望工作城市 | **岗位工作城市** | `cityName`；空值 → `无`（统计时按占位值排除） |

> **为什么保留列名而不是改名？** 因为改名会同时改动 loader / cleaner / analysis / report / viz /
> SQL 模型 / BI 模型——那是在「换数据源」的借口下重写整个项目。本项目的选择是：
> **列名不变，语义在报告的溯源区显式声明**（`config.SOURCE_NOTES` + `report.provenance_lines`），
> 并由测试守住（`tests/test_source_boss.py::test_sample_dataset_runs_through_pipeline` 断言
> 报告的溯源里必须出现「数据口径 … 岗位薪资区间中值」）。

## 3. 薪资解析规则

输入是 Boss 的 `salaryDesc` 字符串，输出 `SalaryRange(raw, lower, upper, months, unit)`，其中 `lower/upper` 一律是**月薪（元）**。

| 输入 | 解析结果 | 说明 |
| --- | --- | --- |
| `15-25K·13薪` | 15000 ~ 25000，`months=13` | 区间中值 20000；年包中值 260000 |
| `8千-1.2万` | 8000 ~ 12000 | **每个数字配相邻单位**，不按尾部单位一刀切 |
| `1.5-2万` | 15000 ~ 20000 | |
| `200-300元/天` | 4350 ~ 6525，`unit=day` | 按制度工作日 **21.75 天**折算月薪；中值 5437.5 |
| `250-350元/天` | 5437.5 ~ 7612.5 | 同上 |
| `15K以上` | 15000 ~ None | 只有下界；中值取下界 |
| `面议` / 空串 / `薪资面议` | None | **不猜**：留空交给清洗层填充，并在 `salary_is_filled` 上留痕 |

月数（`·13薪`、`x14薪`、`*15薪`）只在 **12~24** 之间才被采纳，避免把 `3薪` 这类噪声当成年薪月数。
时薪（`元/时`）按 `8 小时 × 21.75 天` 折算。

## 4. 岗位方向（`专业` 列）映射规则

按标题关键词**顺序**匹配，先命中先归类（表在 `src/sources/boss.py::MAJOR_RULES`）：

| 方向 | 关键词（部分） |
| --- | --- |
| 数据分析 | 数据分析、商业分析、业务分析、数据运营、数据支持、BI |
| 数据开发 | 数据开发、数据仓库、数仓、ETL、数据工程、大数据开发、数据平台 |
| 算法 | 算法、机器学习、深度学习、数据挖掘、NLP、自然语言、计算机视觉、推荐、大模型、AI |
| 数据治理 | 数据治理、数据质量、数据管理、元数据、数据标准 |
| 数据产品 | 数据产品、产品经理 |
| 其他 | 以上都不命中（如「数据标注工程师」「行政专员」） |

**已知误分类风险**：关键词表是启发式规则，标题写法千变万化（例如「数据运营（偏产品）」会被归到数据分析）。
所以报告里这一维度的结论要配合**样本量门槛**看，并且 `data/README.md` 会写明该列是「按标题关键词归类，非官方岗位分类」。

## 5. 岗位吸引力代理分（`满意度评分` 列）

```
基础分 2.0
+ 每个「稳定福利」+0.25（五险一金 / 双休 / 周末双休 / 年终奖 / 补充医疗 / 定期体检，最多计 3 个）
+ 其余福利每个 +0.15（最多计 4 个）
+ 融资阶段属于 {已上市, D轮及以上, C轮, B轮, 不需要融资} ：+0.4
+ 公司规模属于 {1000-9999人, 10000人以上} ：+0.3
截断到 [0, 5]，保留 1 位小数
```

权重以常量写在 `src/sources/boss.py` 顶部（`PROXY_*`），改动必须同步本文件与 `docs/metrics.md`。

**它是什么**：招聘信息本身透露出的「岗位质量信号」强度（福利、融资、规模）。
**它不是什么**：员工满意度、幸福感、留存率——这些岗位数据里根本没有，任何声称有的说法都是编的。
所以它只用于「同一批岗位之间的相对排序」，不能与问卷满意度做跨数据源比较。

想让这一列完全留空？用 `--no-proxy` 生成数据集，清洗层会按中位数填充并标记缺失。

## 6. 采集：怎么做、怎么停、怎么合规

```bash
# 1) 设置 Cookie（登录 zhipin.com 后，从开发者工具 Network 里复制整条 Cookie）
$env:BOSS_COOKIE = "lastCity=101010100; __zp_stoken__=...."

# 2) 抓取（默认每个关键词 × 城市 5 页、每页间隔 4s + 抖动）
#    目标规模：2 个关键词 × 10 个城市 × 5 页 ≈ 单轮 1000~3000 条
python scripts/crawl_boss.py --query 数据分析,数据开发 --city 北京,上海,广州,深圳,杭州,成都,武汉,南京,西安,苏州 --pages 5

# 2') 多轮叠加：一轮跑完等 10 分钟再刷一轮（收集新上架岗位），最多 3 轮、累计 3000 条上限
python scripts/crawl_boss.py --query 数据分析,数据开发 --city 北京,上海,广州,深圳,杭州,成都,武汉,南京,西安,苏州 --pages 5 --rounds 3 --round-wait 600 --max-jobs 3000

# 3) 只看缓存、不联网（CI / 演示用）
python scripts/crawl_boss.py --offline

# 4) 原始 JSONL → 分析口径 CSV
python -m src.sources.boss --raw data/raw/boss/raw_jobs.jsonl --out "data/raw/boss_岗位数据集.csv"

# 5) 跑完整分析（统计 / 体检 / 报告 / 图表）
python main.py --data "data/raw/boss_岗位数据集.csv"
```

设计取舍（与参考项目的差别）：

| 维度 | 参考项目 | 本项目 |
| --- | --- | --- |
| Cookie | 硬编码在 `spiders/boss.py` 里 | 只从环境变量 / `--cookie-file` 读，代码里没有凭据 |
| 中断 | 换 Cookie 后要从头开始 | 逐页落盘，按 `(轮次, 关键词, 城市, 页)` 与 `job_id` 双重去重，**断点续爬**；`--rounds` 可多轮叠加收集新上架岗位 |
| 解析间隔 | 解析写在爬虫回调里 | 原始 JSON 与解析分离（ODS → 适配层），口径可重放 |
| 反爬对抗 | 随机 UA/Cookie 池、`ROBOTSTXT_OBEY=False` | **只礼敬不对抗**：延迟 + 抖动、403 指数退避、遇到安全验证（`code=37`）立即停止 |
| 个人信息 | 有的项目存了招聘者姓名 | 只保留岗位与公司**公开**字段（白名单 `KEEP_FIELDS`），不存招聘者联系方式 |
| 失败可观测 | 打日志 | 明确退出码与提示，已抓数据不丢 |

**合规声明（请务必读完再用）**

- Boss 直聘的用户协议限制自动化抓取。本脚本面向**个人学习、小规模、低频**采样；
- 不绕过验证码、不破解签名、不伪造身份；遇到安全验证就停，这是有意的设计；
- 抓到的数据不要二次分发，更不要用于商业用途；发布仓库时只提交 `data/raw/sample/` 下的手工样例；
- 抓取结果已在 `.gitignore` 中排除（`data/raw/boss/`、`data/raw/boss_岗位数据集.csv`），不会误提交。

### 6.1 详情页 JD、发布时间与采集清单

参考项目的详情抓取是「每条岗位一个请求、没有延迟、失败就跳过」，这里把它做成可控的一步：

| 能力 | 开启方式 | 产物 | 失败分类 |
| --- | --- | --- | --- |
| JD 正文 | `--with-detail` | 原始 JSONL 里的 `jobDescription`；适配层落到 `jd_text` / `jd_len` / `detail_status` | `ok` / `empty` / `verify` / `404` / `403` / `error` |
| 发布时间 | 默认（字段已在白名单） | `publish_date`（`YYYY-MM-DD`） | 解析不出就留空，不推断 |
| 采集清单 | 默认 | `<raw 同名>.manifest.json`（轮次、页数、统计、退出码、时间） | — |
| 多值字段 | 默认 | `skills` / `welfare` 规范成 `|` 拼接，入库时拆成桥表行 | — |

规矩：

1. **详情一天最多抓一轮**：`--detail-delay` 默认 0.8s；遇到 `verify`（安全验证）立即停，不做绕验证码的事。
2. **JD 只存正文**：参考项目把招聘者（`interviewer`）也入库，这里明确不碰任何招聘者个人信息。
3. **manifest 是溯源的一部分**：抓了多少页、失败多少、什么时候抓的，都要能回答「这批数据是怎么来的」。
4. 扩展字段的权威清单在 `src/sources/boss.py::EXTRA_COLUMNS`（25 列），数据库侧一一对应
   `src/db.py::JOB_LAYER_FIELDS`；改一处必须改另一处，`tests/test_source_boss.py::test_map_record_fills_job_market_fields` 会盯着。

## 7. 已知限制（写在报告里，也是面试时的诚实答案）

1. **样本是「在招岗位快照」，不是就业人口**：`n` 条岗位 ≠ `n` 个人；同一家公司重复发岗会放大权重。
2. **薪资是挂牌区间，不是到手薪资**：中值只是区间的算术中点；`13 薪` 只进 `annual_mid`，不改变月薪口径。
3. **薪资缺失不补真值**：`面议` 走中位数填充，只保证「不因缺失丢行」，不代表真实薪资。
4. **代理分不是满意度**（见第 5 节），不能和问卷口径混用。
5. **岗位方向是关键词归类**，存在误分类（见第 4 节）。
6. **抓取受站点策略影响**：Cookie 过期、触发验证都会中断；本仓库只保证「中断可续、口径可重放」。
7. **单期快照，无时间序列**：所有结论都是横截面的描述，不能拿来说「趋势」。
8. **不能做因果**：岗位薪资与学历要求相关 ≠ 学历导致薪资高（观察性数据 + 混杂因素）。

## 8. 与原有核心思路的对应关系（一条都没改）

| 原有核心 | 换数据源后怎么保持 |
| --- | --- |
| 不预置结论、不做预测 | 报告不出现任何预设数字；「不做预测」原则不变（岗位数据更不该预测薪资） |
| 统计推断而非罗列均值 | Welch t + Mann-Whitney U + 95% CI + Cohen's d + Holm，全部照旧，只是数据换成岗位 |
| 样本量门槛（<30 不给结论） | 不变；岗位按城市/方向切分后小分组很容易掉到 30 以下，门槛反而更重要 |
| 数据质量体检 | 不变；换源后新增的可见问题（如某方向样本极少、某城市只有 2 条）会被体检点名 |
| 口径治理 | **加强**：`config.SOURCE_NOTES` + 报告溯源区 + 本文件 + 测试三重约束 |
| 阻断式门禁 / 溯源 / 测试 / CI | 不变；CI 增加「样例 → 数据集 → 分析」的离线端到端步骤 |

## 10. 默认数据源与「一条命令跑通」

从这一版起，**默认数据源就是 Boss 岗位数据**（不再自动加载问卷 CSV）：

| 候选顺序 | 文件 | 说明 |
| --- | --- | --- |
| 1 | `data/raw/boss_岗位数据集.csv` | 本项目自己抓取 + 适配得到的真实岗位数据 |
| 2 | `data/raw/demo_大学生就业数据.csv` | 合成演示数据，仅离线自测/CI 用 |

问卷 CSV（`data/raw/大学生就业数据.csv`）不参与自动探测，需要时用
`python main.py --data data/raw/大学生就业数据.csv` 显式指定。

**一条命令跑通（真实抓取 → 分析）：**

```bash
$env:BOSS_COOKIE = "lastCity=101010100; __zp_stoken__=..."   # 登录后从开发者工具复制
python scripts/crawl_boss.py --query 数据分析 --city 北京,上海 --rounds 3 --to-csv
python main.py
```

`--to-csv` 会调用适配层，把原始 JSONL 直接写成 `data/raw/boss_岗位数据集.csv`；
`main.py` 不带 `--data` 时默认就分析这份文件。也可以分两步做（先抓、后适配），
命令见第 6 节。抓取产物与适配数据集都默认不入库（`.gitignore` 已排除），
仓库里只提交 `data/raw/sample/` 下的手工样例。
